01Resumo executivo
A leitura em 1 minuto

Boa arquitetura. Garantias ainda incompletas.

O projeto tem mecanismos relevantes de confiabilidade: persistência transacional, identidade de jobs, staging antes do commit e gates de CI. Mas uma suíte extensa não elimina contratos quebrados: a migração pode descartar dados não migrados, a limpeza de assets pode deixar referências inválidas e um ACK incompleto pode ser interpretado como persistência confirmada.

O que este relatório comprova. Os achados são sustentados por inspeção estática do snapshot indicado. Os 56 arquivos JavaScript da extensão foram inventariados e tiveram leitura integral ou parcial, discriminada abaixo. Houve truncamento de arquivos grandes e amostragem de testes. Não foi possível concluir uma auditoria integral, linha por linha, nem executar as suítes. Não há aprovação de release ou cobertura medida nesta sessão.

MT-01
Migração parcial apaga o legado e impede nova tentativa
AltoBug confirmadoIntegridade de dados
extension/storage-manager.js:415-479

Falha. Cada gravação malsucedida é absorvida por um catch. Ao final, a flag de migração é sempre gravada. Se apenas uma página tiver sido migrada, todas as coleções legadas do capítulo são removidas, inclusive as páginas que falharam.

Contraexemplo. A gravação da página 0 funciona; a da página 1 falha por quota ou erro transacional. migrated === 1 autoriza a remoção de ambas. Se todas falharem, o legado permanece, mas a flag true bloqueia a migração seguinte. O fallback de restores também usa existência em images, não sucesso da migração, para pular uma página.

Trecho original · storage-manager.js:473-479

}

return { migrated, skipped: false };

Correção. Registrar sucesso e falha por entrada, preservar o legado enquanto houver pendências e confirmar a migração somente após verificar todos os registros. Preferir journal retomável a uma flag binária.

MT-02

AltoBug confirmadoPersistência
extension/storage-manager.js:189-235, 253-259

Falha. O asset anterior da página e o asset anterior de [chapterId, cleanUrl] entram em obsolete. Ambos são apagados sem verificar se outra página ou entrada de restore ainda os referencia.

Contraexemplo. Salvar página 0 com URL U cria asset A. Salvar página 1 com a mesma URL U cria B, substitui o restore e apaga A. MT-03

AltoBug confirmadoContrato IPC
extension/background/jobs-dom-ack.js:15-45, 61-78

Falha. Sem runtime.lastError, qualquer resposta que não tenha ok === false segue para settle(true, 'ack', response). Isso inclui undefined, {} e { ok: true, persisted: false }. O estado durável é marcado com resultPersisted: true antes de avaliar o campo persisted devolvido ao chamador.

MT-08
Título normalizado pode unir capítulos diferentes
AltoBug confirmadoIdentidade de capítulo
extension/cm-chapter.js:5-14, 83-112

Falha. Quando não encontra a URL exata, o gerenciador reutiliza um capítulo do mesmo host com título normalizado equivalente. canonicalTitle remove um prefixo numérico. Por exemplo, “001 - Saga” e “002 - Saga” viram saga, mesmo em URLs de capítulos distintos.

Impacto. O segundo capítulo pode herdar o ID do primeiro e atualizar sua URL. MT-10
Erros internos do roteador nunca chegam ao log: background/log.js não é carregado
AltoBug confirmadoConfiança altaObservabilidade · Parte II
extension/background/router.js:60-61, 81 · extension/background.js (bloco importScripts, aprox. 41-100)

Falha. O roteador resolve seu logger como scope.MangaTranslatorLog ? scope.MangaTranslatorLog.log : function() {}. Esse global só existe se background/log.js for carregado. A lista de importScripts lida em background.js inclui router, state, tab-identity, jobs-*, todas as actions, gtc-* e storage-manager — e não inclui background/log.js. O mesmo vale para o ramo require. O log injetado via contextFactory só alimenta as actions; o logger interno do router permanece um no-op.

Consequência. Em produção, SOURCE_DENIED, ACTION_NOT_FOUND e ACTION_ERROR — este último cobre qualquer exceção lançada dentro de uma action, como 'Aba remetente não é dona do job' em refresh-job-watchdog.js:60 ou falhas de fetch em fetch-image-base64.js — nunca são gravados no translatorLog. O chamador recebe { ok:false, error:{ code:'INTERNAL_ERROR' } }, mas o painel de logs, que é a ferramenta de diagnóstico do projeto, fica cego para esses erros. Além disso background/log.js é, na prática, código morto duplicando o logger interno de background.js.

Evidência insuficiente para concluir a taxa de acerto.

A pergunta decisiva não é “a transação terminou?”, mas “todos os dados ainda fazem sentido juntos?”

async function measure(fn, { iterations = 40, warmup = 8 } = {}) {
  for (let i = 0; i < warmup; i += 1) await fn(i);

    await fn(i);
    samples.push(performance.now() - started);

    p95: percentile(samples, 95),
    samples: samples.length,
  };
}

Melhorias estruturais

E-01 · Registro dinâmico de content scripts por domínio habilitado
Ganho de alcanceRisco médioEsforço grande

Hoje a habilitação por site é uma decisão de runtime tomada depois de 236 KB já terem sido injetados. A permissão scripting já existe. Proposta: remover o bloco de content_scripts de mangá do manifest e manter o conjunto registrado via chrome.scripting.registerContentScripts, sincronizado com enabledDomains em onInstalled/onStartup/storage.onChanged. Ao habilitar um site pelo popup, registrar o padrão e injetar imediatamente na aba atual com executeScript.

Esboço · background (novo módulo content-registration.js)
const MANGA_SCRIPT_ID = 'manga-reader-scripts';
const MANGA_FILES = [
  'gtc-fingerprint.js', 'cm-gtc-client.js', 'cm-dom-replace.js',
  'cm-chapter.js', 'cm-auto-restore.js', 'content_manga.js',
];

async function syncMangaContentScripts() {
  const { enabledDomains = [] } = await chrome.storage.local.get(['enabledDomains']);
  const matches = enabledDomains.flatMap(host => [`*://${host}/*`, `*://*.${host}/*`]);
  const existing = await chrome.scripting.getRegisteredContentScripts({ ids: [MANGA_SCRIPT_ID] });

  if (matches.length === 0) {
    if (existing.length) await chrome.scripting.unregisterContentScripts({ ids: [MANGA_SCRIPT_ID] });
    return;
  }
  const definition = { id: MANGA_SCRIPT_ID, js: MANGA_FILES, matches, runAt: 'document_idle', persistAcrossSessions: true };
  if (existing.length) await chrome.scripting.updateContentScripts([definition]);
  else await chrome.scripting.registerContentScripts([definition]);
}

chrome.runtime.onInstalled.addListener(() => { syncMangaContentScripts(); });
chrome.runtime.onStartup.addListener(() => { syncMangaContentScripts(); });
chrome.storage.onChanged.addListener((changes, area) => {
  if (area === 'local' && changes.enabledDomains) syncMangaContentScripts();
});

Trade-offs. (1) O popup precisa detectar “site não habilitado” sem depender de um content script presente — hoje ele já trata esse caso com a tela de habilitação. (2) host_permissions continua amplo, a menos que se migre para permissões opcionais por host, o que exige prompt ao usuário. (3) Os E2E que assumem injeção estática precisam registrar o domínio de teste antes. O ganho é a única forma de tornar o custo em sites não habilitados igual a zero.

24Principais conclusões
Síntese sem remover os detalhes

Em uma página.

  1. A extensão custa para quem não a usa. Seis content scripts (~236 KB) e um despertar do service worker com escrita de log acontecem em toda página de todo site (manifest.json:29-40, content_manga.js bootstrap, background.js · onMessage). É o gargalo de maior alcance e tem uma mitigação de duas linhas e uma solução estrutural.
  2. Há perda de dados possível na persistência. MT-01 e MT-02 são contradições demonstráveis no storage-manager.js; MT-03 permite marcar como persistido algo que não foi confirmado.
  3. O protocolo de confirmação é permissivo e tem corridas prováveis. ACK ambíguo (MT-03), escrita não aguardada (R-07) e RMW concorrente por progresso (R-06) atacam a mesma chave de estado. A correção é uma fila de escrita por chave.
  4. Erros internos do worker estão invisíveis. O roteador loga em no-op porque background/log.js nunca é carregado (MT-10). Qualquer diagnóstico feito pelo painel de logs subestima falhas.
  5. Cerca de 3,7 s por página são espera por relógio. Substituir por espera por condição é a maior alavanca de latência e não toca em nenhum invariante.
  6. O Base64 de cada página cruza a fronteira de processo quatro vezes. Persistir no worker remove metade dos saltos e desacopla o commit da aba do mangá.
  7. Identidade por normalização destrutiva colide. URLs (MT-04) e títulos (MT-08) podem unir coisas diferentes; a chave deve preservar o que distingue.
  8. Não há vazamento de memória confirmado nem dependência de runtime. Caches são limitados, observers são desconectados, e o runtime é JavaScript puro. Os desperdícios são de CPU, IPC e storage, não de retenção.
  9. A suíte de testes é ampla, mas parte dela verifica cópias. Isso não anula os testes reais (staging, storage, quarentena, E2E com fixture); apenas impede tratar “verde” como prova.
  10. Nada disto foi medido. Todas as estimativas de ganho vêm da estrutura do código. A Fase 0 do plano existe para que a aceitação seja por número, não por leitura.
25Conclusões da auditoria
Só o que a evidência sustenta

Mais confiança começa com garantias menores e reais.

O projeto tem uma base promissora.
A prioridade é impedir que um sucesso aparente esconda uma perda real.

1. A persistência tem defeitos materiais. MT-01 demonstra remoção do legado após migração parcial e bloqueio de retry. MT-02 demonstra referência pendurada após troca de asset. A transação IDB é uma boa base, mas os invariantes de dados precisam ser corrigidos. Evidências: extension/storage-manager.js:189-235, 415-479.

2. O protocolo de sucesso está permissivo demais. MT-03 aceita ACK sem prova explícita de persistência. MT-05 confunde controle e estado; MT-07 aceita exportação sem nenhum arquivo concluído. Corrigir esses predicados vale mais que simplesmente elevar um percentual global. Evidências: extension/background/jobs-dom-ack.js:15-78, extension/gemini/temporary-chat.js:81-105 e extension/background/actions/export-all.js:12-35.

3. Identidade não pode depender de normalização destrutiva. MT-04 e MT-08 mostram colisões determinísticas de URL e título. Preservar semântica de recurso e capítulo evita restauração errada e sobrescrita. Evidências: extension/cm-dom-replace.js:7-36 e extension/cm-chapter.js:5-14, 83-112.

4. A suíte tem valor real, mas qualidade desigual. Há testes importando módulos reais e verificando estados relevantes. Também há espelhos, smoke de lógica simulada e um runner que absorve falhas de hook. A conclusão correta não é “nenhum teste serve”; é “quantidade e verde não bastam”. Evidências: tests/smoke/smoke-03-chapter-persistence.js:21-66, tests/unit/content-manga/get-clean-url.test.js:20-29 e tests/visual-v3/runner.js:41-80.

5. O CI é mais forte que um simples npm test, mas a release precisa ser vinculada a ele. Inventário e cobertura possuem gates explícitos; o workflow de publicação não exige aprovação do mesmo SHA. Evidências: tests/ci/run-jest-ci.js:74-129, tests/ci/verify-coverage.js:94-187 e .github/workflows/publish.yml:3-51.

6. Há espaço grande e seguro para velocidade. A soma dos atrasos fixos declarados no código resulta em cerca de 3,7 s de espera artificial por página, antes de qualquer geração do modelo — derivado de extension/gemini/job-runner.js e extension/gemini/editor.js:118-123, não medido. Os cinco papéis especialistas mapearam 33 melhorias; as de maior alavanca (espera por condição no lugar de sleep, leituras concorrentes em IndexedDB, pré-filtro na busca perceptual e altura real das páginas no leitor) não tocam em nenhum invariante de robustez. Duas exigem cuidado explícito: OPT-01 muda valores de hash e precisa de versionamento, e OPT-33 muda comportamento observável. Ver seção 14 e seção 15.

7. O custo em sites não habilitados é real e evitável. A injeção estática em <all_urls> (extension/manifest.json:29-40) somada ao GET_TAB_ID de bootstrap e ao log TAB_ID_OBSERVED no worker faz cada navegação custar parse de ~236 KB, um possível cold start de 34 arquivos e uma leitura+escrita de translatorLog. É a única conclusão desta auditoria cujo impacto atinge o usuário fora do fluxo de tradução.

8. O worker está parcialmente cego. background/log.js não é importado e o roteador cai no logger vazio (extension/background/router.js:60-61, 81): exceções de actions e negações de origem não aparecem no painel de logs. Qualquer validação manual baseada nesse painel deve ser relida à luz de MT-10.

9. Sem vazamentos confirmados, sem dependências de runtime. As estruturas encontradas são limitadas e limpas; o desperdício está em CPU, IPC e storage. Para os trechos truncados de content_manga.js e popup.js: Evidência insuficiente para concluir.

10. Nenhum ganho deve ser aceito sem medição. As estimativas de desempenho desta auditoria são derivadas de leitura de código. Os testes de performance atuais usam amostras únicas de tempo de parede (tests/integration/performance.test.js:39-45), o que é frágil como oráculo. Instrumentar o ciclo de vida do job e adotar orçamentos por percentil é pré-requisito, não etapa final.

Parecer final. Recomenda-se corrigir os riscos de dados e os falsos sucessos antes de tratar uma nova release como validada. Esta é uma recomendação de engenharia baseada no código, não uma reprovação observada das suítes. Para declarar cobertura atual, ausência de vulnerabilidades, conformidade de todo o repositório ou funcionamento real do Gemini: Evidência insuficiente para concluir.
