0. Método, agentes e retificações

Execução multiagente — declaração honesta. O ambiente desta auditoria oferece apenas ferramentas de leitura web (web_fetch/web_search) e de arquivos locais. Não existe ferramenta para instanciar subagentes nem para selecionar modelos; portanto não foi possível delegar trabalho a "Claude Opus", "GPT" ou "Gemini" em nenhuma configuração. A divisão sugerida (Bugs · Desempenho · Arquitetura/APIs · Recursos/memória/DOM/rede · Refatorações) foi aplicada como cinco passadas de revisão sequenciais e independentes, feitas pelo mesmo modelo, cada uma com checklist próprio; os achados de cada passada foram depois confrontados entre si e com o código antes de entrar neste documento. A afirmação feita numa resposta anterior desta conversa de que "5 agentes foram executados" estava incorreta e fica aqui retificada.

Retificações de conteúdo em relação ao relatório anterior:

  • O item antes descrito como "race condition em mutate()/patch()" foi reexaminado. O defeito estrutural real está na ordem de captura do snapshot entre syncState() e mutate() (ver B1), não em patch().
  • O "leak de memória no reader" foi rebaixado para retenção limitada e provável (ver B10): a análise mostra retenção apenas das imagens que estavam em busca no momento do scroll, não crescimento ilimitado.
  • Nenhum comando do projeto foi executado (não há shell). Todos os comandos aparecem como Não executado.

Sobre números de linha. A ferramenta de leitura devolveu alguns arquivos com quebras de linha preservadas (ex.: state.js, router.js, jobs-watchdog.js, jobs-dom-ack.js, tab-identity.js, cm-auto-restore.js, content_gemini.js, actions) e outros com o espaço em branco colapsado (ex.: background.js, content_manga.js, storage-manager.js, popup.js, reader.js, job-runner.js). Para os primeiros, as referências arquivo:linha resultam de contagem manual sobre o texto bruto (margem ±2 linhas). Para os segundos, a evidência é citada por símbolo/função e por trecho literal, para não inventar números de linha.

Principais conclusões

  1. O projeto é arquitetonicamente maduro para MV3: estado durável com journal, reconciliação após suspensão, identidade canônica de abas, watchdog por chrome.alarms, ACK durável antes de finalizar, roteador de mensagens com validação de payload e origem, persistência transacional em IndexedDB com assets separados. Isto é raro em extensões open-source.
  2. O ponto mais grave está na camada de persistência de estado (background/state.js): syncState() captura o snapshot no momento da chamada e o grava mais tarde na fila, enquanto mutate() captura dentro da fila. Uma syncState() enfileirada atrás de um mutate() grava um estado anterior à mutação, regredindo o mt_state persistido. Correção de uma linha (B1).
  3. O maior custo sistêmico não está no Gemini, e sim em toda página que o usuário visita: seis content scripts (~130 KB não minificados) são injetados em <all_urls> mesmo em domínios não habilitados, e cada carga faz IPC + leituras de storage (G1).
  4. A imagem traduzida (data URL de vários MB) cruza o IPC 3 a 4 vezes e é armazenada duas vezes (Blob no storage-manager + string base64 no cache GTC) (G3). É a maior oportunidade estrutural de redução de CPU, memória e disco.
  5. O sistema de log é um gargalo confirmado de I/O: cada entrada faz leitura+reescrita de até 500 registros em chrome.storage.local; um único job Gemini emite dezenas de entradas (G2).
  6. Há duplicação real (não cosmética): getCleanUrl, generateImageFingerprint, SHA-256 puro, generateId, decodificadores de data URL, tratamento de alarme watchdog e reconciliação legada existem em 2–4 cópias (§23).
  7. Segurança: sem XSS/eval confirmados; dois pontos de fragilidade objetivos — classificação de origem por substring da URL do remetente (B6) e host de teste http://127.0.0.1/* recebendo os scripts de automação Gemini no manifest de produção (B7).
  8. Testes: a suíte é extensa (baseline de 836 testes Jest, 5 shards E2E, smoke, visual, contrato de CI), mas não há evidência de teste que cubra a ordem syncState×mutate nem a re-execução do auto-restore durante uma passada em andamento; testes específicos são propostos em §27.

Limitações importantes (detalhe em §31)

  • Análise 100 % estática; nenhum benchmark, nenhuma execução de Jest/Playwright; comportamento de suspensão do SW e do keep-alive só é confirmável em runtime.
  • Trechos centrais de background.js, content_manga.js, jobs-lifecycle.js, gtc-indexeddb.js e gtc-fingerprint.js vieram truncados pela ferramenta; conclusões sobre esses trechos são marcadas com confiança média ou "evidência insuficiente".

2. Principais bugs e erros

AltoBug confirmado (estrutural)Confiança altaB1 — syncState() pode gravar um snapshot anterior ao último mutate()
extension/background/state.js:90-95 (syncState) · state.js:100-111 (mutate)

Evidência (literal):

function syncState() {
    const snapshot = get();                       // ← capturado AGORA
    const write = () => chrome.storage.local.set({ mt_state: snapshot }).then(() => snapshot);
    _persistenceChain = _persistenceChain.then(write, write);   // ← gravado DEPOIS
    return _persistenceChain;
}
function mutate(mutator) {
    const run = async () => {
        const result = await mutator(get());      // ← capturado só quando chega a vez na fila
        if (result && typeof result === 'object') patch(result);
        const snapshot = get();
        await chrome.storage.local.set({ mt_state: snapshot });
        return snapshot;
    };
    _persistenceChain = _persistenceChain.then(run, run);
    return _persistenceChain;
}

Problema: as duas primitivas compartilham a mesma fila, mas com semânticas de captura opostas. Sequência: (1) handler A chama mutate(mA) — fica pendente atrás de uma gravação em curso; (2) handler B chama syncState() — o snapshot é capturado sem mA; (3) a fila executa mA e grava o estado novo; (4) a fila executa write e grava o snapshot velho. O estado em memória fica correto, mas mt_state persistido regride.

Quando acontece: com concorrência real de handlers — applyFinalizationAccounting (usa mutate) ao mesmo tempo que stopBatch, reconcileAndContinue, ensureInitialized ou o fluxo de processNextJob (usam syncState). A janela se abre sempre que há gravação em curso na fila, o que é frequente com maxConcurrentJobs > 1.

Consequência: após uma suspensão do Service Worker, a reidratação lê contadores/índice desatualizados: job já finalizado reaparece no jobIndex (reconciliação descarta ou recupera de novo), activeJobsCount incorreto, lote promovido perdido. Os mecanismos de reconciliação mascaram parte do dano, o que explica por que não é percebido como falha visível.

Correção recomendada (1 linha): capturar o snapshot dentro do closure: const write = () => chrome.storage.local.set({ mt_state: get() }). Ver R1.

MédioBug confirmadoConfiança altaB4 — Auto-restore descarta mutações recebidas enquanto uma passada está em andamento
extension/cm-auto-restore.js:43-46 (apply) · :≈99-104 (MutationObserver + debounce 150 ms)
async function apply() {
    if (!isActive()) { disconnect(); return; }
    if (isTranslating() || !config.enabled || ... || running) return;   // ← retorno seco
    running = true;
    try { ... for (const { img, cleanUrl } of pending) { ... await resolveAsset(...) ... } }

Problema: apply() é longa (um await de IPC SM_GET_ASSET por imagem). Mutações que chegam durante a execução disparam o debounce → apply() → return por running === true. Não há flag "reexecutar ao terminar". Imagens inseridas por lazy-load nesse intervalo só serão restauradas quando ocorrer outra mutação futura.

Correção: let rerun = false; — em vez de retornar, marcar rerun = true; no finally, se rerun, agendar nova passada. Ver R3.

O port gemini-keep-alive é aberto uma vez e nenhuma mensagem trafega por ele; após desconexão há uma única tentativa de reconexão (keepAliveReconnectAttempted). Na política de ciclo de vida do MV3 (Chrome ≥ 114), o que estende a vida do worker é o tráfego de mensagens no port (ou eventos da extensão), não a mera conexão. Portanto o efeito real é: um evento onConnect no início do job e outro após a primeira queda. O sistema tolera a morte do worker (estado durável), então isto não é um bug funcional, mas o mecanismo é provavelmente inerte e dá falsa sensação de garantia. Evidência insuficiente para concluir sem observação em runtime.

3. Principais gargalos

AltoGargalo confirmadoConfiança altaG1 — Seis content scripts injetados em toda página da web, habilitada ou não
extension/manifest.json — content_scripts[0] ("matches": ["<all_urls>"], js: gtc-fingerprint.js, cm-gtc-client.js, cm-dom-replace.js, cm-chapter.js, cm-auto-restore.js, content_manga.js) · content_manga.js — topo do IIFE

Custo por página visitada (comprovável pela estrutura): parse+avaliação de ~130 KB de JS não minificado (só content_manga.js tem ~80 KB); um chrome.runtime.sendMessage({action:'GET_TAB_ID'}) (acorda o Service Worker se estiver suspenso!); um chrome.storage.local.get(['imageMinWidth','imageMinHeight']); registro de chrome.storage.onChanged; construção de chapterManager e autoRestorer. Tudo isto ocorre antes de saber se o domínio está em enabledDomains.

Efeito colateral relevante: o GET_TAB_ID em cada aba nova impede o Service Worker de dormir enquanto o usuário navega, aumentando consumo de CPU/memória do navegador como um todo.

Melhoria: (a) manter no manifest apenas um loader de ~1 KB que lê enabledDomains e só então pede ao background a injeção via chrome.scripting.executeScript (a permissão scripting já existe); ou (b) melhor ainda, usar chrome.scripting.registerContentScripts() com matches = domínios habilitados, atualizado quando o usuário habilita/revoga um site no popup/options. Ver E1.

AltoGargalo confirmadoConfiança altaG2 — Cada entrada de log faz read-modify-write de até 500 registros em chrome.storage.local
extension/background.js — log(), _flushLog() · background/actions/log-entry.js (allowedSources any, sem limite de tamanho) · content_manga.js — sendLog/sendAudioLog · gemini/job-runner.js — ~25 chamadas sendLog por job
const data = await chrome.storage.local.get(['translatorLog']);
const entries = data.translatorLog || [];
entries.push(...batch);
if (entries.length > 500) entries.splice(0, entries.length - 500);
await chrome.storage.local.set({ translatorLog: entries });

Análise de custo: cada flush desserializa e reserializa O(500) objetos (cada um com extra arbitrário). O batching interno (_logQueue.splice) só agrupa entradas que chegam durante um flush em curso; em regime normal cada log() vira um ciclo get+set. Um job Gemini emite ~25 logs (ATTACHMENT_*, GEMINI_STEP_*, GEMINI_EXTRACT_STAGE por tentativa, etc.); o módulo de áudio emite 3–5 por lote; o content script emite por imagem. Em um lote de 20 páginas com 2 jobs paralelos são centenas de ciclos de storage disputando a mesma fila de I/O de mt_state, wd_data_*, gemini_job_*.

Agravante no popup: popup.js registra chrome.storage.onChanged em translatorLog e chama renderLogs() → relê os 500 registros e reconstrói até 500 nós com innerHTML a cada gravação enquanto a aba de logs está aberta (G7).

Melhoria: buffer em memória + flush por tempo (ex. 1–2 s) e por tamanho; nível mínimo persistido configurável (gravar info só com debugMode); chrome.storage.session para o buffer quente. Ver R2.

AltoGargalo confirmadoProblema arquiteturalConfiança altaG3 — A imagem traduzida atravessa o IPC 3–4 vezes como data URL e é armazenada em duplicidade
gemini/job-runner.js — stageAndCommitResult (GEMINI_IMAGE_EXTRACTED, src) · jobs-dom-ack.js:54-61 (UPDATE_IMAGE, newSrc) · content_manga.js — handler UPDATE_IMAGE → persistTranslatedPage (SM_SAVE_PAGE, dataUrl) e saveGlobalTranslationCacheEntry (GTC_SAVE, translatedDataUrl) · storage-manager.js — dataUrlToBlob (loop charCodeAt) · gtc-indexeddb.js — entry.translatedDataUrl

Caminho atual de um resultado de ~2–6 MB (PNG base64):

  1. Aba Gemini → SW: GEMINI_IMAGE_EXTRACTED { src } (clonagem estrutural 1)
  2. SW → aba do mangá: UPDATE_IMAGE { newSrc } (clonagem 2)
  3. Aba do mangá → SW: SM_SAVE_PAGE { dataUrl } (clonagem 3) → atob + loop JS byte a byte → Blob → IndexedDB
  4. Aba do mangá → SW: GTC_SAVE … translatedDataUrl (clonagem 4) → gravado como string base64 em outro banco IndexedDB

Custos comprováveis: 4 cópias transitórias do payload em memória de processos diferentes; 1 decodificação base64 em JS por página; 2 cópias persistentes por página (Blob no manga_translator_data + string base64 ≈ 1,33× maior no manga_translator_gtc) ⇒ ≈ 2,3× o tamanho real em disco. Para 500 páginas de 3 MB reais: ≈ 3,5 GB em vez de 1,5 GB.

Melhoria estrutural (ver E2): o SW já detém o payload no passo 1 e é o dono do storage-manager: persistir primeiro no SW (precisa do chapterId, que pode viajar no START_BATCH), depois entregar à aba { assetId, newSrc }; o GTC passa a referenciar assetId (ou a gravar Blob). Isso elimina os passos 3 e 4, metade da memória transitória e ~57 % do disco, e torna a persistência independente de a aba do mangá estar viva (hoje o caso "imagem não está no DOM" ainda exige o content script para gravar).

MédioGargalo provávelConfiança alta (na estrutura)G4 — Travessias completas do DOM (incluindo shadow roots) repetidas em alta frequência na aba Gemini
gemini/dom.js:≈66-88 (findAllDeep — walk recursivo de todo o documento) · gemini/job-runner.js — selectLiveComposer() chamado a cada 250 ms em waitForStableComposer(); attachmentSnapshot() chamado dentro de cada sendLog de anexo (3 findAllDeep por chamada); waitForElement() faz observeDeepRoots() + queryFirstDeep() a cada lote de mutações · gemini/observer.js — safeQueryAll via findAllDeep

Complexidade: cada findAllDeep é O(N) sobre todos os nós do documento; selectLiveComposer faz um walk e depois sobe até 5 níveis; attachmentSnapshot faz três walks (inputs, imageInputs, previews) e é invocado em cada onAttempt e em cada log de contexto. Em waitForElement, a callback do MutationObserver faz dois walks completos por lote de mutações, num app Angular que muta continuamente durante a geração (streaming de tokens, spinners) — O(N × mutações).

Impacto: restrito à aba Gemini (não afeta o site de mangá), mas concorre com a própria renderização do Gemini e alonga o caminho crítico de cada job.

Melhoria provável: memoizar o composer estável após waitForStableComposer; coalescer as inspeções de waitForElement num único requestAnimationFrame/microtask por lote; restringir a raiz dos walks ao container da conversa quando conhecido. Exige benchmark para quantificar.

chrome.storage.local.get(['debugMode'], d => { _persistInfo = d.debugMode === true; });

function log(level, source, action, detail, extra = {}) {
    level = level || 'info';
    if (level === 'info' && !_persistInfo) return;          // info só em debug
    _logQueue.push({ id: generateId(), ts: Date.now(), level, source: source || 'bg',
                     action: action || 'UNKNOWN', detail: String(detail || '').slice(0, 300), extra: extra || {} });
    if (_logQueue.length >= LOG_FLUSH_MAX) return void _flushLog();
    if (_logTimer === null) _logTimer = setTimeout(_flushLog, LOG_FLUSH_MS);
}
async function _flushLog() {
    if (_logTimer !== null) { clearTimeout(_logTimer); _logTimer = null; }
    if (_logFlushing || _logQueue.length === 0) return;
    _logFlushing = true;
    try {
        const batch = _logQueue.splice(0, _logQueue.length);
        const { translatorLog = [] } = await chrome.storage.local.get(['translatorLog']);
        const entries = translatorLog.concat(batch);
        if (entries.length > LOG_CAP) entries.splice(0, entries.length - LOG_CAP);
        await chrome.storage.local.set({ translatorLog: entries });
    } catch (_e) {} finally {
        _logFlushing = false;
        if (_logQueue.length) _logTimer = setTimeout(_flushLog, LOG_FLUSH_MS);
    }
}

Razão: converte N gravações em ⌈N/40⌉ ou uma a cada 1,5 s; remove logs info do caminho persistente fora de depuração; limita detail. Trade-off: até 1,5 s de log podem se perder se o SW morrer abruptamente (erros/warn continuam sendo gravados; pode-se forçar flush imediato para level==='error'). O painel de logs do popup deixa de mostrar info sem debug — comportamento a documentar.

async function fetchImageBlob(url, { credentials = 'omit', cache = 'default', timeoutMs = 30_000, maxBytes = 50 * 1024 * 1024 } = {}) {
    const controller = new AbortController();
    const timer = setTimeout(() => controller.abort(), timeoutMs);
    try {
        const resp = await fetch(url, { signal: controller.signal, credentials, cache });
        if (!resp.ok) throw new Error(`HTTP ${resp.status}`);
        const type = resp.headers.get('content-type') || '';
        if (!type.startsWith('image/')) throw new Error(`Content-Type inválido: ${type}`);
        const len = Number(resp.headers.get('content-length'));
        if (Number.isFinite(len) && len > maxBytes) throw new Error('Imagem muito grande');
        const blob = await resp.blob();
        if (blob.size > maxBytes) throw new Error('Imagem muito grande');
        return blob;
    } finally { clearTimeout(timer); }
}

E1 — Injeção de content scripts sob demanda (G1)

Proposta: remover o grupo <all_urls> do manifest. No background, manter um registro dinâmico:

    const matches = enabledDomains.map(h => `*://${h}/*`);

Combinar com optional_host_permissions: ["<all_urls>"] e chrome.permissions.request({ origins: [...] }) no clique "Habilitar site" (gesto do usuário disponível no popup). E2 — Persistir no Service Worker antes da entrega; GTC por referência (G3)

E3 — Um único paradigma de mutação de estado (B2)

Substituir EXPORT_ALL_AND_SHOW { allDownloads: [{url:dataUrl,...}] } por EXPORT_CHAPTERS { chapterIds }; o SW itera getChapterPageIndex, gera a data URL de uma página por vez (blobToDataUrl) e a entrega ao downloads.download com concorrência 3 (R6). E6 — Consulta GTC unificada e fingerprint fatiado (G5, fluxo 9.2)

33. Conclusões da Auditoria

Sustentado por evidência

  1. Existe um defeito estrutural na persistência de estado (state.js:90-95 vs 100-111): syncState() pode gravar um snapshot anterior a um mutate() pendente. A correção é de uma linha (R1) e deve ser a primeira ação.
  2. O custo mais amplo da extensão é pago fora do seu caso de uso: seis content scripts (~130 KB) e um despertar do Service Worker por página visitada em qualquer site (manifest <all_urls>, GET_TAB_ID no boot). A injeção dinâmica por domínio habilitado (E1) remove esse custo sem perder funcionalidade.
  3. O resultado traduzido é transportado e armazenado em duplicidade: 3–4 travessias de IPC como data URL e duas cópias persistentes (Blob + string base64). A persistência no Service Worker com GTC por referência (E2) é a maior otimização de memória e disco disponível.
  4. O log é o maior consumidor de operações de storage (RMW de 500 entradas por evento; dezenas de eventos por job). Buffer + flush temporizado (R2) resolve com risco baixo.
  5. Há quatro bugs/riscos médios confirmados com correções pequenas: reexecução do auto-restore (B4), fetch sem timeout/limite no fingerprint do SW (B8), classificação de origem por substring (B6) e host de teste no manifest de produção (B7).
  6. A duplicação é real e mensurável: getCleanUrl, fingerprint completo, SHA-256 puro, três decodificadores de data URL, quatro generateId, um bloco de watchdog inalcançável, um caminho de dispatch do router nunca usado, e um módulo (cm-gtc-client.js) injetado em toda página com forte indício de não uso.
  7. A arquitetura MV3 é sólida: estado durável com journal, reconciliação, identidade canônica de abas, watchdog por alarmes, ACK antes de finalizar, commit idempotente, storage transacional, reader virtualizado, injeção de dependências e roteador com validação. As melhorias propostas são incrementais e compatíveis com essa base.
  8. Segurança: sem XSS, eval ou vazamento de segredo confirmados; sem dependências de runtime; CSP padrão. Os pontos B6/B7 são de endurecimento, não de exploração ativa.
  9. CI/CD é acima da média (gates independentes, contrato de CI testado, inventário de testes, sharding), com lacunas em lint, build e validação de hosts do manifest.

Evidência insuficiente para concluir

  • Se o keep-alive por port tem algum efeito prático no ciclo de vida do SW (B9) — exige observação em runtime.
  • Se fingerprints são recalculados em rescans do popup e se são computados em paralelo ou em série (trecho de content_manga.js truncado).
  • A complexidade real do lookup perceptual no repositório IndexedDB do GTC (código não lido; só a versão em memória foi vista).
